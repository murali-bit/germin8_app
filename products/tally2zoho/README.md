# Accounting Migration Platform (TallyPrime to Zoho Books)

First working slice of the MVP. See `PROJECT_PLAN.md` for the full plan.

## Run it

Open two terminals.

Terminal 1, the API server (port 3001):

```bash
cd server
npm install
npm start
```

Terminal 2, the website (port 5173):

```bash
cd frontend
npm install
npm run dev
```

Then open http://localhost:5173.

## Sign in

The first time the server starts it creates four test users from `server/seed-users.json` (Super Admin, Admin, Migration Analyst, Client Viewer). The emails and passwords are in that file. They are test accounts only: change or remove them before any real use.

## Try the flow

1. New Migration: keep the defaults and click Create and continue. Every step of the guided flow has its own page with Back and Continue (see "Guided flow and addresses" below).
2. Upload Center: upload the files from `sample-data` (01 to 13) into the matching slots.
3. Completeness Check: click Start processing.
4. Processing Status: review record counts and flagged items.
5. Export Center: click Generate files, then download the CSV files.

Files in `sample-data/problem-files` are meant to be rejected or flagged.

Instead of the six master files (01 to 06) you can upload one "All masters" file into "All masters in one file" at the top of the Upload Center. `sample-data/14_all_masters_utf16.json` is a made-up example in the structure of a real TallyPrime 7.1 export.

The three-file flow of a real TallyPrime 7.1 company (made-up examples, see `sample-data/README.txt`): in a new migration upload `15_all_masters_for_transactions_utf16.json` into "All masters in one file", `16_all_transactions_utf16.json` into "All transactions in one file" and `17_trial_balance_report_utf16.json` into the Trial Balance slot, mark Stock Summary not applicable, then process.

## Real TallyPrime 7.1 master exports

Confirmed from a real TallyPrime 7.1 export (Gateway of Tally > E: Export > Masters, Type of Masters: All Masters, File Format: JSON (Data Exchange), Export closing balance as opening: No):

- The file is saved in UTF-16 LE with a byte order mark. Every reader of uploaded files (`tallystream.js`, `parseJsonFile` in `tally.js`) accepts UTF-8, UTF-16 LE and UTF-16 BE, with or without a byte order mark. UTF-16 is converted piece by piece, so large files are still streamed.
- All master types come in one `tallymessage` list, including types the platform does not use (Currency, TDS Rate, Cost Category, IncomeTaxClassification, IncomeTaxSlab, TaxUnit, Godown, Voucher Type). Stock items are typed "Stock Item" (with a space).
- Ledgers, groups and stock items have no top-level `name`: it is in `metadata.name` (and `languagename`). `recordName` in `tally.js` is used everywhere a name is read.
- Contact details are in dated lists: `ledmailingdetails` (mailing name, address lines, state, PIN code, country) and `ledgstregdetails` (GSTIN, registration type, state, place of supply). The latest entry on or before the end of the migration's financial year is used (`contactInfo` in `masters.js`). `partygstin`, `incometaxnumber` (PAN), `contactdetails` and `openingbalance` are read too. The legacy `old*` fields are used only when nothing else has a value. The sample-file shape (top-level `mailingname`, `address`, `ledstatename`, `pincode`, `countryname`) still works.
- Some values carry hidden characters: line breaks (CR LF) at the end of ledger names, mailing names and GSTINs, at the start of address lines, and the invisible character U+FEFF in address lines. Names and mailing names are never changed in the stored Tally data (vouchers refer to them as written). Pick and drop (this phase): by default every Zoho file writes a name exactly as the masters have it, line breaks and spaces included, the same raw value in Customers, Vendors, Chart of Accounts, Invoices, Bills and every journal file, also where a voucher names the ledger without the line break, so the files still match each other. The CSV writer quotes any cell holding a line break, a comma or a quote, so the file stays valid CSV. Names will be filled in from the GST portal later (not built yet). Zoho may reject a name with a line break: then the name can be cleaned in Mapping Studio (opt-in; see "Decisions for the Zoho output", 4). Processing flags a name with a line break (kind `name_hidden_characters`), a name with plain spaces at its start or end (`name_edge_spaces`), and two masters whose names are the same once line breaks, spaces and capital letters are ignored (`possible_duplicate`, saying whether the GSTIN is the same too). Identifiers (GSTIN, PAN, PIN code, state, place of supply, registration type, country) and address lines are written without those characters, and every such row is flagged (`value_cleaned`).
- Contact rows are also flagged when: a GSTIN or PAN does not have its format (`gstin_format`, `pan_format`); the GST registration type is Regular or Composition with no GSTIN (`gst_registered_without_gstin`); Tally wrote "Unknown" as registration type (`gst_registration_unknown`); `partygstin` differs from the GSTIN of the registration entry used (`gstin_conflict`; the entry's GSTIN is written, so GSTIN, GST Treatment and Place of Supply come from one registration); a dated entry newer than the end of the financial year exists, or every entry is later and the earliest was used (`dated_details_newer`, `dated_details_after_year`). An upload warns when ledgers start in Tally (`startingfrom`) after the end of the migration's financial year.
- A Tally group renamed by the user keeps its reserved name (`metadata.reservedname`). Routing, the standard Zoho account type and the "needs a decision" rule (Sundry Debtors, Sundry Creditors and the like) all follow the reserved name.
- Stock items: the unit is `baseunits` (Tally writes its "Not Applicable" marker when there is none); the HSN code is `hsncode` or the latest `hsndetails` entry. When Tally says the HSN is "As per Company/Stock Group", the code is not in the item and the item is flagged.

The "All masters" upload (`PUT /api/migrations/:id/uploads/all_masters`, removed with `DELETE` on the same path) splits the file into the existing datasets: every ledger and group goes to Chart of Accounts (as in a "List of Ledgers (all groups)" export); ledgers under Sundry Debtors, Sundry Creditors and Duties & Taxes, at any depth of sub-group, also go to Customer Master, Vendor Master and Tax Configuration; stock items and units to their own datasets. Other types are counted and listed as kept for reference, not used. The file uploaded last wins for each dataset: the All Masters file replaces datasets uploaded on their own earlier, and a single file uploaded later replaces only its own dataset (both say so). When the file has no Unit records, Units of Measurement is marked not applicable automatically, with the reason. The original file and its checksum are kept, and each dataset records that it came from it. Tally's envelope (`static_variables`) is copied into each dataset, so the company name is checked as for a file uploaded on its own.

## Real TallyPrime 7.1 transaction and Trial Balance exports

Confirmed from real TallyPrime 7.1 exports of one company. The tests use made-up records in the same structure (`server/fixtures/allTransactions.js`, `server/test/transactions.test.js`).

### All transactions in one file

Tally: Gateway of Tally > E: Export > Transactions, Period = the full financial year (Tally offers only the last month by default), File Format: JSON (Data Exchange). The file is UTF-16 LE with a byte order mark and holds every voucher of the period in one `tallymessage` list, all voucher types mixed. Each record has `metadata.type` "Voucher" and the voucher type in `metadata.vchtype` and `vouchertypename`.

The upload (`PUT /api/migrations/:id/uploads/all_transactions`, removed with `DELETE` on the same path) is built like the All Masters upload: the file is read record by record, its checksum and the file as uploaded are kept, and it is split into the voucher datasets, each of which then behaves exactly like a file uploaded on its own (`bundle_kind = 'transactions'` on the dataset). The upload result and the screens show the count per dataset. The later upload wins for a dataset: this file replaces a voucher dataset uploaded on its own earlier and says so; a file uploaded into a single slot later replaces only that dataset.

Routing by voucher type (`server/src/transactions.js`):

- Sales, Purchase, Receipt, Payment, Journal, Contra, Debit Note and Credit Note go to the dataset of that type. Contra Vouchers, Debit Notes, Credit Notes and Other Voucher Types are new datasets. They are optional: they never block processing.
- A voucher type of the company's own (for example "Sales - Export") is followed up to Tally's own type through the "Voucher Type" records of the All Masters file (name in `metadata.name`, the type above it in `parent`, Tally's own name in `metadata.reservedname`; Tally's own types name themselves as parent). Those records are now kept with the All Masters file instead of being listed as not used. When the All Masters file is uploaded or removed after the transactions file, the kept transactions file is sorted again. Sorting again never undoes what the user did since: a dataset replaced by a file uploaded on its own keeps that file, and a dataset the user removed is not put back. Vouchers that the new sorting moves into such a dataset are then in no dataset; they are never dropped silently: the result of the upload says how many, the count is kept with the file (`notPlaced`, and the control total `control`: vouchers in the file = in datasets that come from it + in datasets replaced by a file of their own + in datasets removed later), and processing raises a flagged item (`vouchers_in_no_dataset`). Uploading the All Transactions file again sorts every voucher into its dataset. Voucher files uploaded on their own are checked again when the Voucher Type records change: a file that no longer fits its dataset is kept, with a warning on the upload (`Voucher types changed: ...`), and a voucher that ends up in two datasets is flagged when the data is processed (`voucher_in_two_datasets`).
- Any other Tally voucher type (orders, delivery notes, stock journals, payroll, memorandum and so on), and any type that cannot be traced to one of Tally's own, goes to "Other Voucher Types" and is flagged per type (`voucher_type_no_dataset`, `voucher_type_not_resolved`). Nothing is guessed from the name of a type.
- Receipt, Payment, Contra, Debit Note and Credit Note vouchers go to Manual Journals or wait for a Zoho import sample (see "Receipts, payments, contra and notes" below). Other voucher types are read and kept with no Zoho file. All are stored, counted, cross-checked against the masters (other voucher types are not), shown in the Data Explorer and used in the Trial Balance check (other voucher types are not).
- A voucher type with no vouchers in the file (for example Purchase, when purchases are entered as journals): the file holds every voucher of the period, so it is the evidence that there are none. The dataset is marked not applicable automatically with that reason, unless a file uploaded on its own is in place (which is kept). This is the only way a required voucher dataset can be left without a file. Without an All Transactions file, Sales, Purchase, Receipt, Payment and Journal stay required, because a missing file cannot be told from a forgotten one; removing the All Transactions file removes its automatic marks again. While the All Transactions file is in place and has no vouchers of a type, that dataset never stays blocked: if a file uploaded on its own for it is removed, the automatic mark is put back; if the user undoes the mark, the dataset can be marked again in Completeness Check ("Not applicable (the All Transactions file has none)"), with the file's reason. A required dataset the file has vouchers for, or any required dataset when there is no such file, still cannot be marked by hand.

Voucher lines: a real voucher has its lines in `allledgerentries` (accounting view) or in `ledgerentries` (invoice view, `isinvoice` true), never both. Both are read (`ledgerEntryList` in `tally.js`). If a voucher ever carries both lists, they are not simply added up: the list used is the first under which the voucher balances (`allledgerentries` alone, `ledgerentries` alone, both together), and the voucher is flagged (`voucher_lines_in_both_lists`). The party is the line that names `partyledgername`.

Cancelled, optional and deleted vouchers (`iscancelled`, `isoptional`, `isdeleted`, or the `vchstatusis...` copies; true or "Yes"): kept and counted, flagged as their own kinds (`voucher_cancelled`, `voucher_optional`, `voucher_deleted`), never written to a Zoho file (left out with `left_out_cancelled` and so on), not balance-checked, and left out of the cross-checks, the tax usage and the Trial Balance check. A cancelled or optional journal needs no routing decision.

Names with hidden characters: a master's name can end in a line break (CR LF) that the same name on a voucher or in the Trial Balance does not have. Names are compared by `matchKey` (hidden characters removed, then spaces around the name); neither value is changed. A voucher name that matches a master only that way is treated as the same ledger and reported once (`ledger_name_hidden_characters`), and processing records how many different voucher ledger names matched exactly, only after ignoring hidden characters, or not at all. The customer, vendor and tax sets used for journal suggestions and for Invoices and Bills find such names too.

Journal suggestions (`suggestJournal` in `vouchers.js`): every suggestion carries its reason and a `clear` flag, and nothing is routed without the user's approval. With the Tally group of each ledger known: exactly one vendor ledger credited and no customer, with an expense, purchase or fixed asset ledger debited, is suggested as a Bill (the reason says so, and warns when a tax ledger is credited as well, for example tax deducted at source, because a bill would carry it as a negative row, not as a tax on the bill); exactly one customer ledger debited with a sales or income ledger credited is suggested as an Invoice; a voucher with no customer or vendor is a Manual Journal; everything else (a vendor debited, a customer debited against an expense ledger, a bank or cash ledger on the voucher) is a Manual Journal marked as not clear, with what was seen. A suggested Bill or Invoice that would carry a negative row (a tax ledger or any other ledger on the same side as the party) has `needsCheck` true and says so in its reason. Bulk approval (`POST /journals/accept-suggestions`) works in two named groups: `clear` (the default) approves only suggestions that are clear and carry no such warning; `needs_check` approves the Bills and Invoices with a negative row, when the user asks for exactly that. A suggestion marked as not clear is never approved in bulk. Routing a journal to Bill when the vendor is debited, or to Invoice when the customer is credited, is refused with the reason.

Fields not transferred from a real voucher are listed in groups (bill-wise and bank details, party and address details, reference numbers and dates, GST and other statutory details, Tally internals, other line details). The platform reads: `guid`, `date`, the voucher type, `vouchernumber`, `partyledgername`, `narration`, the three status flags, `reference`, `placeofsupply`, `cmpgststate`, and on each line `ledgername`, `amount`, `ispartyledger`, `ratedetails` and `gsthsnname` (see "Voucher files").

### Trial Balance report

Tally: Display More Reports > Trial Balance, Alt+F5 for the detailed view (so every ledger is listed), Alt+E > Current, with Show Opening Balance, Show Transactions and Show Closing Balance turned on, File Format: JSON (Data Exchange). This is a report export with a different shape (no `tallymessage` list), UTF-16 LE:

```
{ "dspaccbody": { "dspaccline": [ { "dspaccname": { "dspdispname": "<name>" },
    "dspaccinfo": [ { "dspopamt": { "dspopamta": n }, "dspdramt": { "dspdramta": n }, "dspcramt": { "dspcramta": n }, "dspclamt": { "dspclamta": n } } ],
    "grpexplosion": { "dspaccline": [ ...the same, to any depth... ] } } ] } }
```

Sign convention, worked out on the real export: every amount carries Tally's sign, as voucher lines and the masters' opening balances do: a debit is negative. It was established three ways, all without exception on the real file: (1) for every line that names a ledger or a group, the opening amount equals the opening balance of that ledger in the masters, or the sum over the ledgers under that group, with the same sign; (2) the debit column is always a negative number and the credit column a positive one, and closing = opening + debit column + credit column on every line; (3) over the top-level lines the opening amounts add up to zero and so do the closing amounts. An amount object is empty (`{}`) when the column has no figure.

The Trial Balance slot accepts this report as well as the made-up file of `TrialBalanceLine` records (`server/src/trialbalance.js`). The report is flattened into ordinary `TrialBalanceLine` records (name, line number, depth, whether it has lines under it, the line above it, opening, debit total, credit total, closing) stored as the dataset's file; the report as uploaded is kept beside it with its checksum. Amounts are JSON numbers: an uploaded report is parsed so that every amount keeps the digits written in the file (`parseReportText`, using the source text the JSON reader gives for each number), and becomes a decimal from those digits, whatever its size. A figure with more than two decimals is noted on its line. (A report handed over as an already parsed document is read through each number's shortest decimal text; such a number of 2^46 or more cannot hold every paisa and is noted.) The upload result says how many lines were read, how many are ledgers, how many are groups, and whether the report is at ledger level (every lowest line is a ledger).

At processing every line is matched by name to a Ledger or a Group of the masters (exactly, or ignoring hidden characters). A name that is both a ledger and a group is decided by the line having lines under it, then by which of the two sits under the line above, then by which of the two the vouchers agree with; otherwise it is read as the ledger and that is said on the line. The checks, stored per line (`GET /api/migrations/:id/trial-balance`) and shown in the Data Explorer as an indented table:

1. Totals: over the top-level lines, opening debits = opening credits and closing debits = closing credits (`trial_balance_totals`).
2. Movement: for each matched line, the debits and credits of that ledger's voucher lines (for a group: of every ledger under it, at any depth) must equal the report's debit and credit totals (`trial_balance_movement_differs`, with the figures), and opening + movement must equal closing (`trial_balance_closing_differs`). Cancelled, optional and deleted vouchers and other voucher types are not counted.
3. Lines that match nothing (`trial_balance_line_unmatched`), names matched only after ignoring hidden characters (`trial_balance_name_hidden_characters`), and a report that is not at ledger level (`trial_balance_not_ledger_level`) are flagged.

Opening balances reach Zoho Books once each, through the master files: every ledger that is not a customer or vendor carries its opening balance in the Chart of Accounts file (Opening Balance without sign, and Debit or Credit), and customers and vendors carry theirs in the Opening Balance column of the Customers and Vendors files (a customer in credit or a vendor in debit is left empty and flagged, `balance_unusual_side`). The Opening Balances file (`opening_balances_reference_do_not_import.csv`) is therefore a REFERENCE REPORT only: it is still created for checking (and for Reconciliation), marked "do not import" in its notes, the Export Center and the test report, and it is not in the Import Tracker, the Dependency Manager or the import instructions. The former flag `opening_balance_in_two_files` no longer fires. From the made-up file of lines it is built as before (closing balance of every line). From a Tally report it is built ONLY when the report is at ledger level, from the lowest lines matched to a ledger that carry an opening balance, using the OPENING balance column and the ledger's name as the masters write it; otherwise it is not created and a flagged item says why (`opening_balances_not_created`).

### What creating the files says about vouchers

- Control total over every voucher dataset: stored = written to a file (Invoices, Bills, Manual Journals, and the journals of receipts, payments and contra) + left out with a reason + awaiting routing + waiting for a Zoho sample (`waitingForZohoSample`, per module) + kept without a Zoho file (other voucher types). It is checked when the files are created, returned by `POST /generate` (`vouchers`), written to the manifest and the audit entry, shown in the Export Center and given by `GET /voucher-control`, the report and the test report (`voucherControl`).
- Other Voucher Types raise one flagged item with their voucher count (`vouchers_without_zoho_file`). Receipts, payments and notes held for a module with no Zoho sample raise one item per module (`vouchers_waiting_for_zoho_sample`), saying which sample is needed.
- A reversal is never written as an ordinary document: a voucher whose customer is credited is not an invoice, and one whose vendor is debited is not a bill. It is left out with that reason (`left_out_party_side`).
- A ledger on the same side as the party (credited on a bill, debited on an invoice) is written as a negative row and the document is flagged (`negative_row`, naming the ledger and its kind): the total is then the net amount, not the value of the document. Whether Zoho Books accepts negative rows on import has not been verified.
- A tax ledger (under Duties & Taxes) on the party's side, for example tax deducted at source or the liability side of tax under reverse charge, is not a tax rate on a line. On a bill, a ledger whose Tally type of duty/tax is TDS goes to the bill's TDS columns once it is mapped (see "Voucher files" below). Any other is written as a line with a negative amount and no tax, no Zoho tax mapping is asked for it, and one flagged item per ledger gives the voucher count (`tax_ledger_party_side`); how to enter it in Zoho Books (vendor credit, separate journal) is the accountant's decision.
- Tax mapping counts journal vouchers too (a company that enters purchases as journals has every tax line of its bills there), and says on how many vouchers a ledger is a tax row and on how many it is on the party's side. `tax_pair_incomplete` looks at the tax ledgers of the invoices and bills really written, so journals routed to Bill or Invoice are included.
- A document number that more than one Tally voucher brings into the same file (Tally numbers each voucher type on its own) is flagged (`document_number_repeated`), naming the datasets. Both are written with their Tally number.

## What is real and what is not

Real: creating a migration, file upload with validation and checksum, completeness check, processing with a debit-equals-credit check on every voucher, journal voucher routing (Invoice, Bill or Manual Journal, with suggestions and user approval), CSV generation for Customers, Vendors, Chart of Accounts, Items, Invoices, Bills and Manual Journals, row-to-source tracing, audit log, Data Explorer (view stored records), Import Tracker (import order with prerequisites, and a status per file), Reports and Audit (one-page report and audit trail).

Partly real: Payments Received and Payments Made are built from the Zoho import sample that the user uploads (the headings are the sample's own; see "Held vouchers built from an uploaded sample" below). Not real yet: Vendor Credits and Credit Notes stay held, because Zoho does not publish their import columns and their lines and tax have to be tested against a real sample. Invoices, Bills and Manual Journals follow the official Zoho samples (see "Voucher files" below); no real Zoho import of them has been tried yet.

Flow order: New Migration, Upload Center, Completeness Check, Processing Status, Voucher Classification, Export Center. Prepare migration shows the same flow as one checklist.

### Guided flow and addresses

`frontend/src/navigation.js` lists every screen with its address (`#/upload-center`, `#/prepare-migration`; the old `#/screen-15` form works too) and the guided flow, one step per page: New Migration, Prepare migration, Upload Center, Completeness Check, Processing Status, Mapping Studio, Voucher Classification, Export Center, Import Wizard. Each of those pages has a Back and a Continue button at the top and the bottom (the Import Wizard has its own Back and Next, pinned to the bottom). Every move inside the app is added to the browser history, so the browser's Back and Forward buttons and a reload keep the screen. An unknown address or screen id shows a "This page does not exist" page with Go back and Go to Dashboard. A request the running server has no route for (an older server) is reported as such, not as "Not Found".

New Migration: Back from Prepare migration (in the app or the browser) opens the current migration's saved details (`#/new-migration?edit=1`), and saving changes that migration (`PUT /api/migrations/:id` `{ company?, gstin?, financialYear?, method?, startDate? }`, audited as `migration_details_changed` with the old and the new value). The financial year cannot change once a file is uploaded (409): the files were read against it. The company name can change: the uploaded files are checked against the new name again (each upload keeps the company it names, `uploads.file_company`; its company warning is worked out again; the audit entry says how many name a different company), and the form offers "Use the name in the Tally file" when a file names another company. A new migration starts with an empty company name and GSTIN and the last financial year that has ended; unsaved changes on the form are kept for the viewer (session storage) and offered back. The method is recorded only: every file is created whatever is chosen. In-app Back returns through the browser history when it goes back to the page it came from (`history.state.from`), and otherwise replaces the current entry. Creating a migration for a company and financial year that already have one asks first (open the existing one, or create another). The migration start date is typed as day/month/year (or day/month, taking the year from the financial year) or picked from a calendar; it must be inside the financial year, defaults to its first day, and moves to the first day of a newly chosen year when it would fall outside it. It is stored (`start_date`) and shown only: no file is built from it yet.

Frontend tests (`cd frontend && npm test`): addresses, the flow, every screen id used in the app or sent by the server, and the date rules.

Also real since the last update: login with four roles and firm separation, account type decisions and tax name mapping (Mapping Studio), Opening Balances file, Rejection Manager (upload Zoho error file, approve corrections, retry file with only the rejected records), Reconciliation (upload Zoho report, match by name or number), Identifier Tracker, Dependency Manager, Template Library, Template Mapping, Validation Center, Export Catalogue, Company Settings, Users and Roles.

Also real since then (six features):

1. Sub-group lookup for account types. The Chart of Accounts file may also hold Tally Group records. A ledger under a custom sub-group takes the type of its main group. Tally's own groups whose type is an accountant's decision (Sundry Debtors, Sundry Creditors, Bank OCC A/c, Branch / Divisions, Suspense A/c, Misc. Expenses (ASSET)) and their sub-groups never inherit: they need a decision in Mapping Studio.
2. Cross-checks between vouchers and masters, run at the end of processing: ledgers, stock items, units, Trial Balance ledgers and the party on sales and purchase vouchers. One flagged item per missing name. Nothing is blocked or changed.
3. Expected record counts from Tally, per dataset. A count that differs from the file blocks processing and file creation until the file or the number is corrected.
4. Unit mapping: a Tally unit can be written as a different unit in the Zoho Items file. The source record is untouched.
5. Fields not transferred: for each uploaded file, the fields the platform does not use for that dataset are listed. Information only.
6. Amount comparison in Reconciliation. Amounts are compared using an assumed Zoho report format that has not been confirmed against real Zoho Books reports. Customer, Vendor and Item amounts are taken from Tally with their sign; a balance on the unusual side (a customer in credit, a vendor in debit) is flagged and is not compared. A Zoho report check is removed when its file is created again with different contents, or when the data is processed again.

Still static or not built: Tally Export Guide and Help are static pages. Payments Received, Payments Made, Vendor Credits and Credit Notes have no output until Zoho's import samples for them are added (contra vouchers and the other receipts, payments and notes are written as Manual Journals); other voucher types are read and kept with no Zoho file (Tax Configuration, Units and Stock Summary are read for checks only). Large files are not streamed. The dashboard's summary cards and lower rows are sample data.

Assumed file formats (see `server/src/extras.js`, `server/src/zohoerrors.js`, `server/src/zohotb.js`): the Zoho error file is CSV, XLSX or XLS with an identifying column and a message column found by heading, or picked by the user (see "Zoho error files" below); the Zoho Trial Balance export is read the same tolerant way (see "Zoho Trial Balance comparison" below); the per-module Zoho report is a CSV containing the module's identifying column, optionally a column ending in "ID", and optionally one amount column (a heading containing total, amount, balance or value). None of these formats has been confirmed against real Zoho Books files.

Before any real migration:

- The Customers, Vendors, Chart of Accounts and Items files follow the official Zoho Books (India) sample import files in `zoho-samples` (see "Zoho master files" below). The Invoices, Bills and Manual Journals files follow the official samples too (see "Voucher files" below), but no test import into Zoho Books has been made yet.
- The master, voucher and Trial Balance report field names have been confirmed against real TallyPrime 7.1 exports of one company (see above). That company has no inventory entries on vouchers, no custom voucher types and no cancelled or optional vouchers: item lines on vouchers (`allinventoryentries`), and the Stock Summary, still follow sample payloads from Tally help pages. Confirm them against real Tally exports.
- From a real voucher the date, number, type, party, narration, status flags, the supplier's reference number (`reference`), the place of supply (`placeofsupply`), the company's GST state (`cmpgststate`) and the ledger lines (ledger, amount, party flag, the GST rate per duty head in `ratedetails`, the HSN/SAC code in `gsthsnname`) are read. Bill-wise details (`billallocations`: name, bill type, amount) are read for payments and notes. Bank details (`bankallocations`), the reference date, party GSTIN and address, and the other GST details are not transferred; the Upload Center lists them in groups.
- GST Treatment and the state codes are now written as Zoho codes (see "Zoho master files" below).
- The sample data is made up.

## Zoho master files

The default layout of each master file is the official Zoho Books (India) sample, heading for heading and in the same order, including the optional columns that stay empty (`server/src/zoho.js`: `CUSTOMER_HEADERS` 62 columns from `customer_import_sample_data.xls`, `VENDOR_HEADERS` 64 from `vendor_import_sample_data.xls` with Zoho's own spelling "CustomField Value1", `ACCOUNT_HEADERS` 9 from `sample_accounts.csv` with the heading "Account # " ending in a space, `ITEM_HEADERS` 29 from `sample_items2.csv`). The templates carry `verified: true` and `sampleFile`; `server/test/zohotemplates.test.js` compares the headings byte for byte with the sample files when `zoho-samples` is present. Since test 2 the headings follow Zoho's Map Fields page: where the "Field Explanation" sheet of a sample spells a field differently from the sample's first row, the file uses the Explanation spelling (`zohorules.json` `lists.map_field_labels`: customers "Place Of Contact", vendors "Department"), and `server/test/sampleheaders.test.js` compares every generated file with its sample. The Customers and Vendors files leave out a column that is empty on every row (except Display Name, Place Of Contact, Source Of Supply, GST Treatment, Opening Balance and Status; `lists.contact_columns`), so Zoho's Map Fields page lists fewer unmapped columns. Account types come from one table, `lists.account_types` (status of each type) with `lists.account_type_by_tally_group`; a type that is listed but not yet imported is shown in the Assumptions as unconfirmed. The mark applies only while a firm uses the default layout; a changed layout can still be marked by an admin (Template Mapping), as before. A layout saved before this change that names a column that no longer exists (for example `place_of_supply`) keeps working: that column is written empty, shown as "no longer available", and must be given another value or removed before the layout can be saved again; the new standard columns can be added back, or the layout reset.

Values (`server/src/zohocodes.js`), in the formats of the sample rows and their "Field Explanation" sheets; anything not certain is left empty and flagged, never guessed:

- Customers / Vendors: GST Treatment from Tally's registration type, in the code set chosen per firm (see "Decisions for the Zoho output" below). With the default (the import sample codes): Regular -> `business_gst`, `business_sez` for an SEZ party; Composition -> `business_registered_composition`; Unregistered, Consumer, Unregistered/Consumer -> `business_none`; no registration with a country other than India -> `overseas`. A registered type without a GSTIN (`gst_registered_without_gstin`) or with a GSTIN of the wrong format (`gstin_format`), an unregistered type with a GSTIN (`gst_unregistered_with_gstin`), "Unknown" (`gst_registration_unknown`), none (`gst_treatment_not_set`) or another type (`gst_treatment_not_mapped`) leave it empty. Place of Contact (customers) and Source Of Supply (vendors) are Zoho's two-letter state codes, from the place of supply, else the state, else the GSTIN's state; a state with no code (`state_not_mapped`), no state at all (`place_of_contact_missing`) and a place that differs from the GSTIN's state (`place_differs_from_gstin`) are flagged. Currency Code `INR` (a ledger not in rupees is left empty, `currency_not_rupee`), Status `Active`, Payment Terms and "Net N" from Tally's credit period, Billing Address = address line 1 and Billing Street2 = the other lines (no city is invented), Phone and MobilePhone from their own fields.
- Chart of Accounts: customers and vendors (the Sundry Debtors and Sundry Creditors trees, also renamed) are Zoho contacts and are left out (Zoho keeps their balances in Accounts Receivable / Accounts Payable); a ledger left out this way that is not in the Customer or Vendor dataset is flagged (`party_ledger_not_in_contacts`). Duties & Taxes ledgers are written as Other Current Liability and flagged (`tax_ledger_in_accounts`): Zoho creates its own GST tax accounts. Account Type from the existing group logic; Parent Account, Account Code and Account # empty; Description is the ledger's description, else "Tally group: <group>"; Opening Balance with 2 decimals and Debit or Credit.
- Items: Product Type `goods` / `service` (the values of `sample_items2.csv`): the type chosen for the item in Mapping Studio (Rates), else `service` for every item when the migration's business type is services, else from Tally's type of supply (goods when not set). Business type (`PUT /api/migrations/:id/business-type` `{ businessType: 'services' | 'goods' | '' }`, shown in Mapping Studio, Rates): stock items exist only in a trading or manufacturing company; in a service company Tally's items are only descriptions on sales bills. The default is services when the Stock Summary is marked not applicable in the Completeness Check, or when there is no stock data (no Stock Summary file and no inventory line on any voucher), and goods otherwise. A choice is audited (`business_type_changed`); a change of the type the Items file is built with (a choice, or a Stock Summary mark that moves the default) marks the Items file out of date; no other file writes the Product Type. Per item, `PUT .../item-rates` `{ item, productType: 'goods' | 'service' | '' }`. Items written as service by the business type raise one warning (`items_written_as_services`, with how many Tally marks as Goods). HSN/SAC: Tally's code is written when it is a valid one. With none, a code chosen in Mapping Studio (HSN/SAC) for the item or the income ledger is written, else (invoices only) a usual SAC suggested from the words of the name, always listed in the Assumptions for confirmation (`hsn_suggested`); with none of these the line is flagged and blocking (`hsn_missing_required`) while the HSN/SAC field is on in Zoho Books. See "HSN/SAC, Migration Date and GST ledgers (S3)" below. Business type and product type per item are not saved in Mapping Profiles yet. Item Type `Sales and Purchases` (usable on invoices and bills, no inventory tracking), Status `Active`, Rate / Purchase Rate from the standard price and cost when Tally has them. Rates entered in Mapping Studio replace an empty (or different) Tally rate; Account, Purchase Account and the tax preference come from Mapping Studio too (see below). Initial Stock is left empty; an opening stock is flagged (`item_opening_stock_not_written`). `item_rate_missing` is raised while any item has no selling rate, and `item_tax_preference_not_set` while any item has no Taxability Type.

Flags that must be resolved before the import (shown as blocking in the test report's "what to fix next"):

- `display_name_duplicate` / `account_name_duplicate`: two or more rows of the Customers or Vendors file (Display Name), or of the Chart of Accounts (Account Name), WRITTEN with the same name (capital letters ignored): two different Tally records with one name, or names the accountant chose to clean into the same one. Zoho matches contacts by Display Name and does not accept two accounts of the same name, so one would be rejected or merged. Cleared by a decision under possible duplicates (Mapping Studio, Names).

Warnings, not blockers (pick and drop; `NAME_WARNING_KINDS` in `testreport.js`, `warning: true` on the flagged items of `GET /summary`): `display_name_hidden_characters` / `account_name_hidden_characters` (a name written with a line break or hidden character, as in Tally), `display_name_collides_after_cleaning` / `account_name_collides_after_cleaning` (names written differently that are the same only once line breaks, hidden characters, spaces and capital letters are ignored: they matter only if Zoho cleans them on import, or once cleaning is chosen, when they become `*_duplicate`), `mailing_name_hidden_characters`, and the processing flags `name_hidden_characters` and `name_edge_spaces`. The Prepare migration checklist counts names not cleaned as warnings (not open decisions), and the dashboard does not count them as unmatched.
- `item_rate_missing`: items without a selling Rate (and, for `Sales and Purchases`, without a Purchase Rate). Zoho requires a rate, so those rows are expected to be rejected: enter the rates first, or prove with one test import that Zoho accepts them empty.
- `account_without_group`: a ledger with no Tally group has no account type and cannot be decided in Mapping Studio.
- `profit_and_loss_balance_not_written`: Tally's own Profit & Loss A/c ledger is never written to the Chart of Accounts (Zoho keeps the accumulated profit in Retained Earnings); when it has an opening balance, that amount must be entered on Retained Earnings. Without a balance it is only noted (`profit_and_loss_ledger_left_out`).
- `tds_not_mapped`: a TDS ledger credited on bills with no Zoho TDS tax chosen (Mapping Studio, TDS mapping); the TDS is then a negative line. `voucher_layout_outdated`: a voucher layout saved for the earlier placeholder headings.
- `account_type_missing`: a Chart of Accounts row with no Account Type (its Tally group has no decided Zoho type), which Zoho requires. `place_of_supply_missing_taxed`: an invoice or bill whose lines carry GST but which has no place / source / destination of supply, which Zoho needs to tell IGST from CGST + SGST (give the contact a state in Fix contacts).
- `zoho_builtin_account_name`: a Chart of Accounts row whose name matches an account Zoho Books (India) creates itself (for example Advance Tax, TDS Receivable, GST Payable, TDS Payable; list `ZOHO_BUILTIN_ACCOUNTS` in `zohocodes.js`, written from Zoho's published default chart of accounts and NOT yet confirmed in a live organisation), with no decision in Mapping Studio. The row may be rejected as a duplicate, and its opening balance (stated in the flag) would then be missing.

## Decisions for the Zoho output (`server/src/decisions.js`)

Stored apart from the Tally data, applied only to the files, audited with who, the old and the new value, and each change marks the files it affects out of date.

1. GST treatment codes, per firm, admin only (Company Settings; `GET`/`PUT /api/settings/gst-codes`). Zoho's import samples and Zoho's help page list different codes. "As in Zoho's import sample" (default): `business_gst`, `business_registered_composition`, `business_sez`, `business_none` (unregistered and consumer alike), `overseas`. "As on Zoho's help page": `business_registered_regular`, `business_registered_composition`, `business_sez`, `business_unregistered`, `consumer`, `overseas` (`deemed_export`, `tax_deductor`, `sez_developer` are never written: no Tally type means them). With the help page codes a Tally party of type "Unregistered/Consumer" is left empty and flagged (`gst_treatment_ambiguous`) unless the admin decides once how all such parties are written (`unregisteredConsumerAs`). Both sets and their meaning are in `GST_CODE_SETS` (`zohocodes.js`). The setting used is recorded with the Customers and Vendors files (`generated_files.build_settings`); changing it marks only the files built differently out of date, and changing it back clears that.
2. Rates (Mapping Studio; `GET`/`PUT /api/migrations/:id/item-rates`, `POST .../item-rates/paste` with `item name<TAB>rate[<TAB>purchase rate]` lines, `POST .../item-rates/default`, `PUT .../item-accounts`). A rate has at most 2 decimals and is never rounded. The default rate fills only items with no rate in Tally and none entered, each item getting its own entry. The tax preference (Taxability Type `Taxable`, `Non-Taxable`, `Out Of Scope`, `Non-GST Supply`; intra- and inter-state tax names, from the saved Zoho tax list when there is one; an optional GST rate) fills the item tax columns: Intra State Tax Type "Group" and Inter State Tax Type "Simple" (as in Zoho's sample) are written only with a rate.
3. Zoho's own accounts (Mapping Studio; `GET`/`PUT /api/migrations/:id/account-clashes`). For each Chart of Accounts ledger whose name is the name of an account Zoho creates (compared ignoring capital letters, spaces and hidden characters): rename (suggested "<name> (Tally)"; refused when the new name is another Zoho account or another account in the file), use Zoho's own account, or leave as it is (`zoho_builtin_account_kept`). Undecided clashes stay flagged and block the import in the test report. Renamed ledgers and ledgers put on Zoho's account are written that way in the Account column of the voucher files too. A ledger put on Zoho's own account is left out of the Chart of Accounts (`zoho_builtin_account_used`) and, when it has an opening balance, that balance is written to `opening_balances_for_zoho_accounts.csv`: one manual journal (OB-1) in the layout of Zoho's `sample_journals.xls` (15 headings), dated the day before the financial year starts (the date Zoho Books gives to the opening balances it records), with one line per ledger on Zoho's account and one line on Opening Balance Adjustments (where Zoho puts the other side of every opening balance) that balances it. It is imported after the Chart of Accounts. Every opening balance is therefore written exactly once across the Chart of Accounts, Customers, Vendors and this journal. Whether Zoho accepts a manual journal on these accounts and on Opening Balance Adjustments is not confirmed (flagged on the file).

4. Names (Mapping Studio, "Names"; `server/src/names.js`, rules in `server/src/namefix.js`). Pick and drop: names are written exactly as in Tally unless the accountant chooses otherwise here; cleaning is opt-in, for a name Zoho rejects (stored decisions made earlier keep working). Every customer, vendor and Chart of Accounts ledger whose name has a line break, tab, invisible character (U+200B, U+FEFF) or a space at its start or end is listed with the name before and after cleaning (hidden characters shown in words, for example `[line break]`), the kind of file and the number of vouchers that name it (`GET /api/migrations/:id/names`). "Clean" (`PUT .../names` `{ ledger, clean: true|false }`) and "Clean all" (`POST .../names/clean-all`) store the cleaned name: hidden characters become a space, runs of spaces one space, spaces around the name are removed. Possible duplicates are listed per kind (customers, vendors, accounts): names that are the same once cleaned and capital letters are ignored, or two contacts with the same GSTIN (as written, after Fix contacts), each with its Tally group, GSTIN, opening balance, voucher count and the name written. Decisions (`PUT .../duplicates` `{ key, decision: 'keep_both' | 'merge' | null, keep, names }`): "keep both", with a new name for a member where the names would be WRITTEN the same (capital letters ignored; names that differ only by a line break or spaces are written as in Tally and need no new name) (refused when still written the same, when it is another ledger's written name of the same kind, has hidden characters, or, for an account, is the name of one of Zoho's own accounts); "treat as one", where only the kept ledger is written, the opening balances of the others are added to its own (Tally sign; the addition is shown, audited and stated in a flag; a total on the unusual side is left empty and flagged as before), and the vouchers of every member name it (`merged_into_other_contact`, `merged_into_other_account`, `contacts_treated_as_one`, `accounts_treated_as_one`). A ledger with a decision under Zoho's own accounts cannot be merged into another. A decision stored for a group that is no longer in the data is not used and is listed to be removed.
   **One name resolver** (`makeNameResolver`, `ctx.outputName`) writes every name: the Display Name and Company Name (when the mailing name is the ledger name) of Customers and Vendors, the Account Name of the Chart of Accounts, and the party and Account columns of Invoices, Bills and Journals (every voucher file built later must use it too). In order: the decision on a clash with Zoho's own accounts, "treat as one" (the kept ledger's written name), a new name from "keep both", the cleaned name; otherwise the master's name exactly as the masters have it (a name that matches no master: as given). A voucher name is matched to a master exactly, else ignoring hidden characters when exactly one master matches that way. The processing flags about names (`name_hidden_characters`, `name_edge_spaces`, `possible_duplicate`) stay until the data is processed again, but the test report lists only the undecided ones.
5. Fix contacts (Mapping Studio, "Fix contacts"; `GET`/`PUT /api/migrations/:id/contact-fixes` `{ ledger, gstin?, state?, treatment?, reason? }`). The customers and vendors with a problem, filterable by: registered without GSTIN, GSTIN of the wrong format, no state / place of contact / source of supply (also a contact with no state in Tally whose place comes only from its GSTIN), place differing from the GSTIN's state, GST registration unknown or not set, other GST treatment left empty; with the remaining count of each. Per contact: a GSTIN (format check, and its first two digits must be a state in Zoho's list), a state (one of Zoho's codes; refused when a valid GSTIN is from another state), or a GST treatment: "treat as unregistered" (the code for an unregistered business in the chosen code set, `business_none` with the sample codes, `business_unregistered` with the help page codes; no GSTIN is written), or "registered, regular / composition" (needs a valid GSTIN; for a party whose Tally type is unknown or missing). A chosen state becomes the place of contact / source of supply, and the Billing State when Tally has none. Bulk actions: `POST .../contact-fixes/state-from-gstin` (the GSTIN's state for every contact with no state), `POST .../contact-fixes/unregistered-without-gstin` `{ confirmCount }` (refused with the current count when it differs from the one confirmed). Each correction is stored with its reason (typed, or the action's own words), audited with who, old and new, applied only to the Zoho files (flag `contact_details_corrected`, which restates the Tally values), and marks the file(s) of that contact out of date: Customers and Invoices for a customer, Vendors and Bills for a vendor (the Invoices and Bills files write the contact's GST Treatment, GSTIN and state). The GST code set is likewise recorded with the Invoices and Bills files.

## Voucher files (Invoices, Bills, Manual Journals)

`server/src/vouchers.js` (building), `server/src/voucheropts.js` (settings and TDS mapping). The default layouts are the official Zoho Books (India) samples, heading for heading and in the same order: `sample_invoices.xls` (70 headings), `sample_bills.csv` (65), `sample_journals.xls` (15). The two .xls samples are old-style Excel workbooks; `server/fixtures/zohoSamples.js` reads their first row without a library, and `server/test/vouchers.test.js` compares the headings byte for byte. The identifying column is Invoice Number, Bill Number and, for journals, Reference Number (the Tally voucher number). "Item Tax" and "Item Tax %" are different columns (the column id spells "%" as "percent"). Values follow the samples' example rows and "Field Explanation" sheets: dates `yyyy-MM-dd`, amounts with 2 decimals, Zoho's two-letter state codes, Is Inclusive Tax `false` (invoices) / `FALSE` (bills, as in that sample), journals "both" and "published". Every column's source is listed in Template Mapping. Layouts can still only be renamed and reordered. A layout saved for the earlier placeholder headings is still written (columns that no longer exist are empty) and is flagged `voucher_layout_outdated` (blocking) until an admin resets it.

Invoices and Bills: one row per item or account line, no separate tax rows.

- Header: Invoice / Bill Number (the Tally voucher number; for bills the supplier's invoice number from Tally's `reference` when the accountant chooses it in Mapping Studio, Voucher files, and the voucher has one), date, Invoice / Bill Status `open` (posted; an import sends no email) or `draft` when chosen, Customer / Vendor Name through the one name resolver, GST Treatment and GSTIN as written in the Customers / Vendors file (after Fix contacts), Currency Code `INR`, Notes / Vendor Notes from the narration (line breaks and hidden characters become a space, spaces at the ends removed; the same for journal Notes). Invoices: Place of Supply from Tally's place of supply on the voucher, else the customer's Place of Contact (empty for an overseas customer). Bills: Source of Supply = the vendor's Source Of Supply; Destination of Supply = Tally's place of supply, else the company's GST state on the voucher. A missing one is flagged (`place_of_supply_missing`; `place_of_supply_missing_taxed`, blocking, when the document carries GST). A line whose tax does not fit the two states (IGST with the same state on both sides, CGST + SGST between two states; for invoices the company's GST state on the voucher against Place of Supply) is flagged `tax_type_state_mismatch` with both states, and nothing is changed.
- Lines: Account (the ledger, resolved name); a stock item line carries its Item Name (with quantity, unit and rate; when quantity times rate is not the line amount it is flagged, `item_line_rate_differs`); an account line is quantity 1 at its amount, with the account name as description. v2: on INVOICES every line has an Item Name (Zoho's sample marks it mandatory): an account line carries the service item of its account (see "Invoice rules (v2)" below). Bills keep account-only lines (Item Name is optional in the bill sample; one `line_without_item_name` flag per file, not blocking). HSN/SAC: Tally's 4, 6 or 8 digit code (at least 6 digits while the field is on in Zoho Books; a 5-digit SAC is refused by Zoho), else the code chosen or suggested for the item or ledger.
- GST on the lines: the tax ledgers on the other side from the party (not TDS) are put on the line they belong to, as the Zoho tax they are mapped to (Mapping Studio, Tax mapping), with the rate and the type ("ItemAmount" for one ledger such as IGST, "Tax Group" for two or more such as CGST and SGST, as in the samples). All ledgers of a line must map to the same Zoho tax (a GST group for CGST and SGST), otherwise `line_tax_names_differ`. The rate comes from Tally's rate on the line (`ratedetails`, per duty head), else the tax ledger's own rate (`rateoftaxcalculation`), else, for a single line only, from the amounts when exactly one standard GST rate fits (exactly, or within a rupee per ledger). One taxable line carries all the tax. Several lines carry tax only when Tally gives each line its rate and those rates account for each tax ledger's amount (within a rupee per ledger); otherwise nothing is guessed: `tax_not_attributable` and the tax cells of every line are left empty. Also flagged: `tax_rate_unknown`, `tax_amount_differs` (more than rounding), `tax_name_rate_mixed` (one Zoho tax written with several rates). Bills write a Tax Amount per line (Tally's amount for a single line; line amount times rate otherwise, with the paise of rounding on the last line); invoices have no tax amount column, so Zoho works it out.
- Duties & Taxes ledgers whose Tally type of duty/tax is neither GST nor TDS (for example "Others"): never added to the GST of the lines; written as a line of their own on their own account with no tax, flagged `non_gst_duty_on_document`, and not asked for in Tax mapping.
- Reverse charge shape: on a bill, GST ledgers debited and GST ledgers credited (on the vendor side) with the same amount for every duty head. The GST is not written as the vendor's tax and the credited side is not a negative line, so the bill's total is the amount owed to the vendor. Audit fix: the GST debited is put on the lines like a vendor's tax but in the bill's Reverse Charge Tax Name / Rate / Type (the mapped Zoho tax, else Zoho's own GSTnn or IGSTnn of the rate), so Zoho posts the input credit and the tax payable (`reverse_charge_written`, an assumption; turn on reverse charge in GST Settings). When that cannot be done with certainty it is flagged `reverse_charge_bill` as before (and a journal routed by default is then a Manual Journal).
- Invoice lines that are not income (audit fix): a line on an expense, asset or tax ledger (a known non-income kind) goes to the invoice's Adjustment (described with the ledger names), never a negative line with GST0 and a service item on that account (`invoice_line_to_adjustment`; a journal routed by default to Invoice is then a Manual Journal). GST0/IGST0 is written only on a positive income line. TDS deducted by a customer on a ledger with no section goes to the invoice's TDS columns with Professional Fees (194J) by default (`tds_name_default`). CGST without SGST (or the reverse) is flagged `tax_heads_incomplete` (blocking).
- Totals: the Zoho total of each document (lines plus the tax Zoho works out from each rate, less the TDS Zoho works out from the percentage) is compared with Tally's party amount: a rounding difference is written in Adjustment (`zoho_recompute_adjusted`), a larger one flagged (`zoho_recompute_differs`), tax that could not be written flagged `document_total_differs`. Reconciliation's expected amount for Invoices and Bills is that Zoho total, worked out from the rows.
- Negative lines (a ledger on the same side as the party): written as lines with a negative amount and flagged (`negative_row`); the Zoho check calls them "may be refused". v2: round-off ledgers go to the Adjustment column and TDS to the TDS columns (see "Invoice rules (v2)"); a discount is never guessed.

TDS on bills (Mapping Studio, TDS mapping; `GET`/`PUT /api/migrations/:id/tds-mappings` `{ ledger, tdsName, section?, percent? }`, `tdsName: ''` removes): a ledger is a TDS ledger only when Tally's type of duty/tax (`taxtype`) is TDS, never by its name. When it is credited on a bill (the vendor side) and mapped, the bill's TDS Name, TDS Section Code and TDS Percentage come from the mapping and TDS Amount is Tally's amount, so Zoho's bill total (sub total plus tax less TDS) is the amount owed to the vendor. Unmapped: a negative line, flagged `tds_not_mapped` (blocking). Also flagged: `tds_amount_differs` (the mapped percentage of the sub total differs from Tally's amount by more than a rupee), `tds_several_on_bill` (Zoho takes one TDS per bill; both are negative lines), `tds_on_other_side`. A tax ledger on the vendor side that is not TDS in Tally stays `tax_ledger_party_side`. v2: invoices too (see "Invoice rules (v2)"), and with no mapping the Zoho TDS tax suggested from the section in Tally is written (`tds_name_default`), so `tds_not_mapped` remains only for a ledger with no section. The TDS posts to the account Zoho's TDS tax is linked to, not to the account written for the Tally ledger. Whether Zoho computes TDS on the sub total or on the total with tax depends on the organisation; TDS Amount is always written, so it is not worked out again.

Voucher file settings (`GET`/`PUT /api/migrations/:id/voucher-settings` `{ billNumber: 'voucher' | 'reference', documentStatus: 'final' | 'draft' }`): per migration, audited, marking Bills (bill number) or all three voucher files (status) out of date.

Manual Journals: one row per line; Journal Number Prefix and Suffix from the Tally number (everything up to its last run of digits, and that run; `journal_number_not_usable` when it has no trailing digits or is longer than Zoho's 16 characters), Reference Number = the Tally number, Notes = narration (Zoho requires it: "Journal <number> from Tally" when there is none), Journal Type "both", Currency INR, Status "published" (or "draft"). A customer or vendor line is entered on Accounts Receivable / Accounts Payable with the contact in Contact Name, because contacts are not accounts in Zoho.

The Import Wizard says what must exist in Zoho Books first (`zohoSetup` on each import step): the GST taxes and groups, and the TDS taxes, with the names chosen in Mapping Studio. None of this has been tried in a live Zoho Books organisation yet. ONE import order: `importList` (Prepare, test report, dashboard) reads the Import Wizard's plan (`planFor`/`stepPlan`, from `zohorules.json` import_order); a Bills or Invoices file whose lines name no item does not wait for the Items file. Zoho's TDS export can be given (`GET/PUT/DELETE /api/migrations/:id/zoho-tds-taxes`): its names become the TDS pick list and the names written by default.

Journal routing by default (audit fix): a purchase journal whose ONE TDS ledger has a Zoho TDS tax (chosen, or suggested from its section) is a Bill with the TDS in the TDS columns; reverse charge is a Bill with the Reverse Charge columns. Voucher Classification and Prepare read the default routing from the same build as the files (`defaultDecision`, `defaultFallback`). Answers worked out from the whole migration (`/prepare`, `/assumptions`, the journal list, the voucher build) are kept while nothing changes (SQLite's change counter is the signature). A change to invoices or bills also marks the journals (and, for invoices, the Items file) out of date. Downloads of a file with rows the Zoho check expects Zoho to refuse need "Download anyway" on the server too (`POST zoho-check/acknowledge` for the file as it is, or `?confirmed=1`); a viewer's download changes no import status.

## TDS, reverse charge and Zoho's own recomputation (second test import, `server/src/tds.js`, `server/src/vouchers.js`)

Zoho Books refused 101 bill rows and 2 invoices with "Enter the required TDS details.", 11 bills with "IGST cannot be applied as this is an intrastate transaction", and two vendors' payables did not tie to the files. Nothing below names a company: every rule reads Tally fields (the ledger's nature of payment and rate, the TDS amount, the GST duty head, the party's GST registration and state, the voucher date), the tables in `zohorules.json` and the settings of the migration.

- **TDS** (`tds.js`). Every row with a TDS Amount carries TDS Name, TDS Percentage and TDS Section Code (rules BIL-TDS-THREE-TOGETHER and INV-TDS-THREE-TOGETHER, confirmed by test 2). Percentage, in this order: chosen in Mapping Studio; the rate Tally's own amount shows (amount divided by the base, when exactly one standard rate fits to the paisa, else within the rupee Tally rounds to); the rate on the Tally ledger; the rate of the matching tax in Zoho's TDS export; the usual rate of the section (`lists.tds.nature_table`). Section code: exactly what Zoho's TDS export says for the matching tax; else the section number (194J) for a document dated before 01/04/2026, the Income Tax Act 2025 code (professional_fees) from that date (setting "Form of the TDS section code": by date, always old, always new). The section comes from Tally's nature of payment (a section number in it, else its plain words: table `lists.tds.nature_words`, assumed, listed in the Assumptions), then a section number in the ledger name, then (TDS deducted by a customer, no section) the rate, then the table's default. The source of each value is in the Assumptions list (`tds_details_filled`); a value that cannot be worked out is blocking (`tds_details_missing`), and a journal routed by default stays a Manual Journal.
- **TDS names.** Zoho already has taxes of its own (`lists.tds.zoho_default_taxes`, seen in the test org: for example Commission or Brokerage at 2%, new act). A tax the tool would create with the name of another Zoho tax (another rate or section) is written with section and rate in the name ("Commission or Brokerage 194H 5%", `tds_tax_name_made_unique`). A tax the organisation's export (or Zoho's defaults) has for that section, rate and date is used under its own name and section code, even when two taxes share one name. Rule BIL-/INV-TDS-NAME-NOT-ZOHO-DEFAULT (warning) checks the same on a finished file. The taxes the files name, with rate, section code, tax act and start date, and whether the export has them, are listed in the Import Wizard (set-up, TDS taxes), in the download zip's README, and at `GET /api/migrations/:id/tds-taxes-to-create`.
- **Reverse charge** (`vouchers.js`). The tax of the Reverse Charge columns is chosen from the two states, not from the duty head Tally booked: inside one state a GST tax group, between two states IGST (`rcm_tax_type_changed`); amounts never change. A vendor with no state and Tally IGST: setting "Reverse charge on a vendor with no state" (GST, the default, because Zoho reads an empty Source of Supply of an unregistered vendor as inside the state; or IGST as an import of services, the bill written as overseas) (`rcm_state_unknown_assumed`). An overseas vendor keeps IGST. If the organisation's tax list has no tax to write instead, nothing is invented and `tax_type_state_mismatch` is raised. Rule BIL-RCM-INTRA-INTER (confirmed by test 2) predicts the refusal on a finished file.
- **Zoho recomputes tax and TDS.** Zoho takes the tax of each line from its rate and amount and TDS from the TDS percentage and its base (the sub total, or the total with tax: setting "What Zoho works TDS out on"), and ignores Tally's amounts. The builder works out Zoho's figures per document and compares them with Tally's to the paisa. A rounding difference (up to one rupee per taxed line and per TDS) is written in the Adjustment column so the total equals Tally's (`zoho_recompute_adjusted`; setting "Rounding differences": adjust or flag only). A larger one is never hidden: `zoho_recompute_differs` says the two parts, the document total in Zoho and the two ways out (accept Zoho's figure, or correct Tally). The documents are listed in `recomputeDocs` of the voucher build, in the flagged items and in Voucher Reconciliation (reason "Zoho works tax and TDS out itself"). On the real data of test 2 this found the bills of two vendors whose totals differed from Tally (both since fixed: one tax rate taken from Tally's amounts, one GST base that included a duty line).

## Voucher Reconciliation (`server/src/voucherrecon.js`, screen Voucher Reconciliation)

Whatever came out of Tally in JSON must be in the Zoho files, or be accounted for. Linked from the Sidebar, the Export Center, Prepare migration (step 5), Completeness Check (All Transactions file) and the Dashboard.

- When the files are created, `buildVoucherOutput` records for every voucher where it went (`recon`): written to Invoices, Bills, Manual Journals or the journals of receipts, payments and contra (with the document number written: Invoice / Bill Number, or the journal's Reference Number), held for a Zoho module with no import sample, waiting for a routing decision, or left out with a reason (`cancelled`, `optional`, `deleted`, `not_balanced`, `party_side`, `no_single_party`, `party_amount_unreadable`, `no_lines`); vouchers of a type with no Zoho file are recorded as kept. For a written voucher it also records how each Tally line (`voucherLines`) is written (`row`, `negative_row`, `party`, `tax_column`, `tds_column`, `tax_not_written`, `reverse_charge_not_written`, `not_written_zero`) and what the document posts once imported (debit and credit: every row and its tax, the TDS credited on a bill, the party at the document total; for journals the Debit and Credit cells). This is stored in `voucher_recon` with the files and removed with them (also when the data is processed again).
- `GET /api/migrations/:id/voucher-reconciliation` works it out on every request from the vouchers stored now and that record: per voucher type the count in, the count per destination, the reasons for leaving out, the total accounted for and Matches / Does not match; the same for Tally lines (and Tally's amount per kind of line); and the amounts: debit and credit in, not written, of the vouchers written (in Tally) and as written, with each difference explained (reverse-charge GST not written, tax not put on a row, tax worked out from the rates differing, item quantity times rate, rounding, or not explained). A reason is accepted only when the size fits: reverse-charge and unmapped tax must equal the Tally amounts of those lines (debit and credit each), within one rupee per tax line written on an invoice or bill that has a tax column, else within half a paisa per line (journals); rounding gets the same allowance; anything else is not explained. `held`: per Zoho module waiting for a sample, the vouchers, Tally debit and credit, the sample needed and what to import first. Checks: every row adds up; no voucher is in two files or both in a file and held (`generated_rows`, `held_vouchers`); the vouchers and rows of each file agree with the file; each file has one document number per voucher written (Zoho groups rows by it); the Debit and Credit cells of the journal files equal what their vouchers post; a voucher recorded as written without its posting is a problem; the held lists agree; the voucher control total of the Export Center (`voucherControl`) agrees; the All Transactions file's voucher count; amounts in = written + not written; every difference explained. `outOfDate` (with the reasons) when a voucher file is out of date.
- `GET .../voucher-reconciliation/vouchers?slot=&bucket=&page=&pageSize=` (up to 200): the vouchers behind a cell, by date and number: date, voucher number, Tally type, where it went, Zoho file, document number written, Tally and written amounts, the reason left out or the difference, and the flagged items written for that voucher. `bucket`: `all`, `written:<file>`, `held:<module>`, `awaiting_routing`, `left_out`, `left_out:<reason>`, `no_file`, `difference`, `difference:<reason>`, `problem`, `role:<line kind>`. A migration with files but no vouchers has a reconciliation with zero totals.
- `GET .../voucher-reconciliation/report.csv`: the held list, the summary tables, the checks and every voucher (audited as a download). It starts with a byte order mark for Excel, and text cells that start with = + - @ get a leading apostrophe so Excel does not run them as formulas (only this report; the Zoho files are written as they are). Viewers can read all three.

## Receipts, payments, contra and notes (`server/src/payments.js`)

Zoho's import samples in `zoho-samples` cover Customers, Vendors, Chart of Accounts, Items, Invoices, Bills and Manual Journals. There is NO sample for Payments Received (customer payments), Payments Made (vendor payments), Vendor Credits or Credit Notes, so none of their columns is invented (`SAMPLE_NEEDED`).

**The default route (setting `paymentsRoute: 'journals'`, Voucher files): nothing is held.** Every receipt from a customer, payment to a vendor, debit note and credit note is written NOW as a Manual Journal in `journals_receipts_payments_contra.csv`: the party on Accounts Receivable or Accounts Payable with the Contact Name, the bank and every other line as Tally posted them (Zoho Books accepted this shape in the third test import). Which invoice or bill each one settles (Tally's bill-wise allocations) is in `credits_to_apply.csv` (not for import) and on the Import Wizard page "Apply the credits". The list below is the other route, `paymentsRoute: 'module_files'`, for when Zoho's samples are uploaded: the vouchers marked "held" then wait for the file built from the sample.

- Receipt: exactly one customer credited, no vendor, exactly one bank or cash ledger debited (the Deposit To account) -> Payments Received, held. No customer and no vendor (a loan, income, a refund) -> Manual Journal (`receipt_not_from_customer`).
- Payment: exactly one vendor debited, no customer, exactly one bank or cash ledger credited (Paid Through) -> Payments Made, held. No customer and no vendor (expenses, salaries, taxes, transfers) -> Manual Journal (`payment_not_to_vendor`).
- Contra: always a Manual Journal (bank and cash transfers; there is no transfer sample).
- Debit Note: party a vendor, debited -> Vendor Credits, held. Party a customer -> Manual Journal on Accounts Receivable, flagged (`note_written_as_journal`). Credit Note: the mirror (customer -> Credit Notes, held; vendor -> Manual Journal, flagged). No party -> Manual Journal.
- Anything else (two parties, no bank or cash ledger, two bank ledgers, a party on the unexpected side, a refund) is never guessed: a Manual Journal, which posts exactly what Tally posted, flagged with what was seen (`money_voucher_unclear`).
- A bank or cash ledger is one whose Tally group chain reaches Bank Accounts, Bank OD A/c, Bank OCC A/c or Cash-in-Hand.

The Manual Journals go to their own file, `journals_receipts_payments_contra.csv` (key `other_journals`), in the layout of `sample_journals.xls` and with the same values as the Manual Journals file, except that Reference Number and the journal number carry the code of the voucher type before the Tally number (RCT-, PMT-, CTR-, DN-, CN-; Payment "24/0012" is prefix "PMT-24/", suffix "0012", Reference Number "PMT-24/0012"), because Tally numbers each voucher type on its own and Zoho would otherwise read Payment 12 and Contra 12 as one journal. Notes fall back to "<voucher type> <number> from Tally". The groups written as a matter of course raise one flagged item each (`vouchers_written_as_journals`). It is imported after the Manual Journals file; the name decisions, the decisions on Zoho's own accounts and the document status mark it out of date like the other voucher files; Reconciliation compares it like the journals (each journal's debits).

Held vouchers (`held_vouchers`, written when the files are created): counted in the voucher control total as `waitingForZohoSample`, listed in the Export Center ("Payments files from Zoho's import sample", with the sample needed and the place in the import order), the Dependency Manager, the Import Instructions, the crosswalk (status "Waiting for a Zoho sample") and the test report (`waitingForZohoSample`, and one line in "what to fix next"). Their place in the import order is kept: Payments Received after Invoices, Payments Made and Vendor Credits after Bills, Credit Notes after Invoices.

Vouchers in no file yet are an OPEN item, never "accounted for" (`server/src/heldvouchers.js`): `GET /api/migrations/:id/held-vouchers` gives `{ written, held, awaitingRouting, notInAnyFile, words: "<written> written to files, <n> not in any file yet", modules: [{ key, module, vouchers, amount, sample, importAfterModule, sampleReceived }] }` from the voucher control total; `GET .../held-vouchers/<module>.csv` lists them (date, number, party, amount, bank) to enter by hand (audited as a download); `PUT .../zoho-samples/<module>` takes Zoho's import sample (CSV or XLSX whose first row is a heading row), stores it under `zoho-samples/received/` (`ZOHO_SAMPLES_DIR` overrides the folder) and audits it (`zoho_sample_received`): the file for that module is NOT built yet. Prepare migration has the item "Vouchers not in any file yet" (and `held`, `zohoCheck` with the Zoho check's will / may counts), the Import Wizard a step "Not in any file yet" before "Compare the trial balances" (address `#/import-wizard?step=held`; every wizard step is in the address), and the Dashboard, Zoho check, Export Center, Voucher Reconciliation and the completeness table ("Not in any file yet") say it.

Bill-wise allocations of a held voucher (its party line's `billallocations`), worked out now so the file can be built as soon as the sample is added: an "Agst Ref" names a reference created by a "New Ref" on the same party; it is applied to the invoice or bill WRITTEN that carries that New Ref on its party line, under the number written (Invoice Number, or the Bill Number chosen in Voucher files). Vouchers are applied in date order, each amount at most up to what is left of the document's Zoho total (for a bill, after TDS). Not applied, and flagged on the voucher: a reference no voucher of the migration created (a document from before the period, part of the opening balance: `allocation_bill_not_in_migration`), a reference created by a voucher not written as an invoice or bill (for example a journal written as a Manual Journal, unrouted or left out: `allocation_document_not_written`), an amount more than is left (`allocation_exceeds_document`), an allocation on the other side from the party (`allocation_sign_unclear`). "New Ref", "Advance" and "On Account" stay unapplied (advances, money on account). Other lines on a held voucher (bank charges, tax deducted) are flagged (`money_voucher_other_lines`): whether the module's file can carry them is known only from its sample.

`GET /api/migrations/:id/payments` (`?file=`, `?limit=`): the samples needed, what the files created last hold (per module: vouchers, amount, applied, unapplied, allocations), and the same worked out from the current data, with every held voucher (party and bank as written, amount, the invoices or bills it settles, what stays unapplied and why).

## Journal review (Voucher Classification)

`server/src/journalreview.js` (rules), routes in `server/src/index.js`. Every journal voucher is listed with its lines (the ledger name shown without hidden characters, the name written in the Zoho files through the one name resolver, the ledger's own Tally group, debit and credit), its debit total, which kinds of party are on it, its suggestion with the plain reason, its decision and who made it.

- `GET /api/migrations/:id/journals/review` filters (`state` undecided | decided | all | not_posted, `review` clear | needs_check | not_clear, `suggestion`, `decision`, `party` customer | vendor | both | none, `ledger` (hidden characters and capitals ignored), `pattern`, `min` / `max` amount, `from` / `to` date yyyy-mm-dd, `q` search in number, narration and ledger names), sorts (`sort` date | number | amount | suggestion | decision, `dir`; ties are broken by date, number and file order, so pages are stable) and pages (`page`, `pageSize` up to 200). It also returns the counts over all journals, the ledgers used, the patterns, and `matchingIds` (every filtered journal that can be decided, for "select all that match"). A wrong filter is refused (400) in words.
- The PATTERN of a journal is the set of Tally groups debited and the set credited (each ledger's own group; "(not in the masters)" for a ledger with none), whatever the amounts or the number of lines.
- `POST .../journals/bulk` `{ ids, decision, preview?, confirmCount? }` (the selected journals; another decision is replaced) and `POST .../journals/pattern` `{ recordId, decision, includeDecided?, preview?, confirmCount? }` (every journal with the same pattern; by default only those without a decision). Without `confirmCount` they only say what would happen: how many change, how many already have that decision or another one, how many are cancelled or optional, how many are refused (a vendor debited is not a bill, a customer credited is not an invoice: the same rule as for one journal), how many would still be left out of the file (not balanced, no single customer or vendor) and how many would be made out to a ledger that is not a customer (vendor) in the masters. The decision is made only when `confirmCount` equals the number that would change (409 with the new numbers otherwise). Each journal changed is audited (`journal_routed`: who, the decision it had, the new one, the suggestion, and how it was made) and the action once more (`journals_bulk_routed`); the files affected are marked out of date.
- A journal whose default fell back to a Manual Journal although the suggestion was a Bill or Invoice says why (`defaultFallbackWords`). "Accept as per Tally" for journal routing is on the journal card; a review made before the files were read again says "accepted before the files were read again" (`beforeReprocess`), here, on every decision card and on Prepare migration.
- The screen: filter buttons and lists with their counts, search, sort, pages of 25 to 200, select one, a page or all that match, "route the selected to" with a confirmation showing the count and the reasons, "same decision for this pattern" with a preview, and keys (j / k or the arrows to move, x select, 1 Invoice, 2 Bill, 3 Manual Journal, a accept the suggestion, p pattern, [ and ] pages, / search, Esc close). Viewers read only. "Accept the clear suggestions" and "accept the ones with a negative row" are unchanged.

## The zero-decision path (v2, `server/src/defaults.js`)

Every open decision has an automatic, Zoho-safe default, so a migration where nobody decides anything still produces files Zoho Books is expected to accept. A decision made by a person always wins. Each default applied is a flagged item on its record, an audit entry (`default_applied`) and a line of "Assumptions the tool made" (`GET /api/migrations/:id/assumptions`: count per kind, whether to check it, whether it is unconfirmed until the next test import, and the screen section where it is changed), shown on Prepare migration and in the Export Center. The rules, one small function each: ledgers named like Zoho's own accounts use Zoho's account (bulk "all: use Zoho's own" or "all: rename"); Bank and Credit Card accounts carry no opening balance in the Chart of Accounts (it is in the opening balance journal, and listed plainly by `GET /api/migrations/:id/bank-opening-balances` to be typed in Settings > Opening Balances); items with no rate get Rate 0.00, Item Type "Sales" for a services business unless a purchase account and rate are known; a valid GSTIN means registered and gives the state; two contacts with the same Display Name in one file are one party; journals take the clear suggestion, else (and for reimbursements, and when the document would carry a row Zoho refuses) a Manual Journal; the Bill Number is the supplier's invoice number, unique per vendor; the Bills file has no Total, SubTotal, Balance or Item Total column; an HSN/SAC value that is not 4, 6 or 8 digits is not written as it is: a code chosen for the item or ledger is written instead (`GET/PUT /api/migrations/:id/hsn-corrections` for old -> new corrections, `PUT .../hsn-defaults` for the code per item or ledger), else a suggestion that you confirm; a bill line of a registered vendor with no GST gets GST0 or IGST0 (or the exemption or reverse charge chosen in the voucher file settings); vouchers outside the financial year are left out by default (switch in the voucher file settings). Reading the files again keeps the journal routing decisions by Tally voucher; the ones that no longer match are listed on Prepare migration (`process-status` `journalDecisions`).

## Mapping Profiles (`server/src/profiles.js`, screen Mapping Profiles)

A viewer limited to one client company sees, opens and downloads only the profiles saved from that company's migrations; the preview is also a `GET` (`GET /api/migrations/:id/profiles/:pid/preview`), so a viewer can read it, but not apply. A profile is the decisions of one migration saved under a name for the firm (`POST /api/migrations/:id/profiles` `{ name, description?, includeClientSpecific?, replaceProfileId? }`), so the next client starts from them. It holds: account types decided per Tally group, tax mappings, TDS mappings, unit mappings, item rates and tax preferences, the Items accounts, the decisions on Zoho's own accounts, the voucher file settings, and journal routing by PATTERN (the Tally groups debited and credited; a pattern is saved only when every decided journal of it went the same way, otherwise it is listed as not saved; single journals are never saved). For reference only, never applied: the firm's GST treatment code set and column layouts (firm settings, changed in Company Settings and Template Mapping). Client-specific corrections (names cleaned, possible-duplicate decisions, contact fixes) are saved only when "include client-specific corrections" is ticked.

Applying is two steps. `POST /api/migrations/:id/profiles/:pid/preview` lists every entry with its status: will be applied, already the same, decided differently here (conflict), matches nothing in this migration, reference only. Names are matched exactly, else ignoring hidden characters, else ignoring capital letters and spaces, the last two only when exactly one name fits (the preview says how). `POST .../apply` `{ replace: [entry id], confirmCount }` applies the entries to apply plus the conflicts named in `replace` (every other conflict is kept); it is refused (409) when the count differs from the preview. Each entry is sent through the same route a person uses on the screen, so it is checked, audited (who, old, new) and marks the affected files out of date exactly as a manual decision; a refused entry is listed with the screen's reason. One `profile_applied` audit entry records the whole. Profiles are listed with `GET /api/profiles`, renamed with `PUT /api/profiles/:pid`, deleted (admin or the person who saved it) with `DELETE /api/profiles/:pid`, downloaded as JSON with `GET /api/profiles/:pid/export` and read back with `POST /api/profiles/import` `{ profile, name? }` (the file is checked field by field; unknown fields are dropped). Viewers read only.

## Zoho Trial Balance comparison (`server/src/zohotb.js`, Reconciliation)

`PUT /api/migrations/:id/zoho-trial-balance?basis=closing|opening` with the Trial Balance exported from Zoho Books (CSV, XLSX or XLS). THE LAYOUT OF ZOHO'S EXPORT IS ASSUMED until a real export is tried. The heading row may be below title rows; the account column is found by heading ("Account Name", "Account", "Particulars"...; never a code, number, type or ID column); the figures are a debit and a credit column (preferring "net", then "closing"), or one balance column whose figures carry Dr / Cr. A balance without Dr / Cr is never guessed: the user says whether a positive figure is a debit or a credit (`balanceSign`). When the columns cannot be found or more than one fits, the answer is 422 with the headings, and the user picks them (`accountColumn`, `debitColumn`, `creditColumn`, `balanceColumn`). Rows with no figure (headings) and rows named "Total ..." are left out and counted; unreadable rows are listed. The Zoho rows are stored; the comparison is worked out on every `GET`, so it always follows the current decisions. `PUT .../basis` switches between Tally's closing and opening column; `DELETE` removes the report.

The Tally side is the ledger lines of the Tally Trial Balance report, each under the name the Zoho files give it: customers as one Accounts Receivable total and vendors as one Accounts Payable total, every other ledger through the one name resolver (renamed, cleaned, treated as one, or Zoho's own account). Tally's Profit & Loss A/c is listed as not compared. The result: accounts that agree, accounts that differ (both figures and Zoho less Tally), only in Tally, only in Zoho (Opening Balance Adjustments and Zoho's own accounts are explained), and the debit and credit totals of both sides. Tax ledgers carry a note that GST on the lines posts to Zoho's own tax accounts.

## Zoho error files (`server/src/zohoerrors.js`, Rejection Manager)

`PUT /api/migrations/:id/rejections/:key` now reads CSV, XLSX or XLS. THE LAYOUT OF ZOHO'S ERROR FILE IS ASSUMED until a real one is tried. The heading row is the first of the first 20 rows holding the identifying column (its heading as written in the file imported, compared without capitals, spaces and punctuation); the message column is the first heading saying error, then reason, message, remark, failure or problem. When either is missing the answer is 422 with `needsColumns` and the headings, and the user picks them (`?idColumn=&errorColumn=`). One rejection is stored per record, with every different message. `GET /api/migrations/:id/rejections/groups` groups them by CAUSE (the message with the record's own values, quoted text, GSTINs, e-mail addresses and numbers replaced) and gives each cause one suggested action and the place where it is fixed: Fix contacts, Names, Zoho's own accounts, Rates, Tax mapping, TDS mapping, Account types, Units, Voucher Classification, the Import Tracker, Company Settings (GST treatment codes), or a correction by hand in the Rejection Manager. It also says, per file, which columns were used and how they were found.

Zoho's real error file layout is now known from the first test import (ROWNUMBER, where the heading row is row 1, then ERRORMESSAGE, then the columns of the imported file). Such a file is also explained by ROOT CAUSE (`explained` in the groups answer, shown first in the Rejection Manager): each message is matched to a rule through `lists.error_messages` of `zohorules.json`; "This error is related to Row N - <column>" rows are counted as follow-on rows of row N; a row refused only because the account, contact or item it names was refused in an earlier error file (for example a journal on a bank account refused in the Chart of Accounts) is a cascade. Each cause has its count, a plain explanation, the fix and the screen.

## Zoho check (`server/src/zohocheck.js`, `server/src/zohocheckapi.js`, screen Zoho check)

Every rule of `server/src/zohorules.json` (documented in `docs/ZOHO_IMPORT_RULES.md`) is applied to every row of every Zoho file, because Zoho reports only one error per row. Kinds: required, enum, regex/format, max length, unique within the file, conditional, forbidden, and references across files (a name a voucher file uses must be in the master file being imported, or be one of Zoho's own accounts or taxes). A document is refused as a whole when one of its lines is; a row naming a master row that will be refused is a cascade of that row. Each cause is "Will be refused" (confirmed by our import or stated by Zoho), "May be refused" (assumed, or only Zoho Books can confirm it) or a warning. Rules about Zoho Books settings are listed as not checked, never dropped silently.

- The check runs by itself when the files are created and is stored with a signature of the files; it is out of date exactly when the files are.
- `GET /api/migrations/:id/zoho-check`: per file rows, documents, expected to import, may be refused, will be refused, %, and the causes grouped across files (count, message, fix, evidence, screen).
- `GET /api/migrations/:id/zoho-check/rows?file=&cause=&page=&pageSize=`: the rows behind one cause (row number as in Zoho's error file, the record, the columns).
- `GET /api/migrations/:id/zoho-check/findings.csv`: every finding (BOM for Excel; text that Excel would run as a formula is prefixed with an apostrophe).
- `POST /api/migrations/:id/zoho-check/acknowledge`: the Export Center asks before downloading a file with rows Zoho will refuse; downloading anyway is written to the audit log. A viewer cannot acknowledge: the screens send `?confirmed=1` with a viewer's download, and the server then writes only the audit log (no confirmation is stored, so the viewer's next download asks again).
- `preSteps` in the summary: what to do by hand in Zoho Books before an import. No rule asks for one now (the "Long Term Liability" account was one; Zoho Books India has no such type and the tool writes "Non Current Liability"), but the mechanism stays for a future rule.
- A TDS Name that cannot be checked (no TDS mapping and no Zoho TDS export) is one "may be refused" cause per file whose fix says "Create these TDS taxes in Zoho with these names, or upload Zoho's TDS export" and lists each name with its section and rate (`tdsTaxes`; the section from the file, else from the pick list); its "Fix" opens the wizard's set-up step, where the export is uploaded (N TDS taxes read, Remove to undo).
- Speed: a synthetic 50,000-row journal file (3.8 MB) is parsed in about 40 ms and checked in about 170 ms.
- Replay against the first real import: 465 of 467 refused documents predicted, no accepted row blocked by a confirmed rule; the 2 not predicted were one "Long Term Liability" account and the journal that used it. Test 2 found the cause (the type does not exist in India), and the Zoho check now refuses any Account Type that is not in `lists.account_types`.

## Import Wizard, Download all and the completeness table (`server/src/importwizard.js`, `server/src/completenesstable.js`, `server/src/zipstore.js`)

Screen Import Wizard (`#/import-wizard`, `Screen40_ImportWizard.jsx`) is the last page of the guided flow. It replaces Dependency Manager, Import Instructions and Import Tracker: their old addresses open it. One step per page, a step list on the side (done, locked, rows refused), Back / Next and "Step n of N" pinned to the bottom of the page. The step the person is on is kept on the server per migration (viewers move without saving).

- Steps, from `zohorules.json` (`organisation_setup`, `import_order`, `modules.<file>`): Set up Zoho Books (one tick per sentence of each set-up item, with its click path; financial year and opening balance date of this migration shown; optional upload of Zoho's own Chart of Accounts export), then one step per file in the rules' order, the bank accounts check (after the Chart of Accounts), Save the Migration Date (the date Zoho Books shows is typed and checked; a hard lock on every later file), Opening balances (the opening balance journal OB-1, and OB-2 for customers in credit and vendors in debit; the same balances as a list to type only when there is no journal file or Zoho Books refused it), Apply the credits (a list, not an import), and Compare the trial balances (the trial balance Zoho Books should show, worked out before any import; what is still open; finished when the Zoho Trial Balance comparison shows no difference).
- Each file step: Download; the rows and documents of the file (a bill is its number AND its vendor, as the Zoho check counts it); the click path in Zoho Books; what to choose on Zoho's import screens and why (skip duplicates, encoding, auto-numbering not ticked), the columns not to map; the rows expected and, when the Zoho check answers, the rows it expects Zoho to accept and refuse; "What happened in Zoho?" (rows imported, rows refused, Mark as imported, Undo, upload Zoho's error file with its causes).
- Locking: a step is locked until every file it depends on is imported with no refused rows (and, for journals and the opening balances, every bank account is ticked as present in Zoho Books). The reason is said plainly ("Needs Chart of Accounts. 2 rows were refused in Chart of Accounts. Fix those first."). It can be opened with a typed reason. Ticks, results, overrides and uploads are in the audit log; viewers can read only.
- `zohoExistingAccounts(db, jobId)` (importwizard.js): the accounts the new Zoho organisation already has, from the uploaded export, else the researched default list.
- `GET /api/migrations/:id/import-wizard`, `PUT .../import-wizard/current`, `PUT .../import-wizard/ticks`, `PUT|DELETE .../import-wizard/results/:key`, `PUT|DELETE .../import-wizard/overrides/:step`, `GET|PUT|DELETE .../import-wizard/zoho-accounts`.
- `GET /api/migrations/:id/download-all`: one zip (stored entries, CRC-32 from node:zlib, no library) of every current file numbered in import order (`01_chart_of_accounts.csv` ...), with `READ_ME_FIRST.txt` (what to do in Zoho Books before the first import, written from the company's own data) and `READ_ME_IMPORT_ORDER.txt` (the order and the click path of each file; it also lists the payment files built from an uploaded sample); reports for checking only go in `not_for_import/`; an out-of-date file is left out and the read-me says so. Checked to open with Python's zipfile and PowerShell's Expand-Archive.
- `GET /api/migrations/:id/completeness-table` (and `.csv`): one row per dataset (Chart of Accounts, Customers, Vendors, Items, each voucher type): count in Tally, count in the Zoho files, difference; amount in Tally, amount in the files, difference (masters: net opening balance; vouchers: total of debits); status Matches, Explained (the reasons with counts: merged duplicates, accounts Zoho already has, held for a missing Zoho sample, outside the financial year...) or Not matched with a link to the detail. Vouchers come from the voucher reconciliation; nothing is worked out a second way. Shown on Processing Status, the Export Center and the first and last step of the wizard.
- "Create files" is one shared component (`components/CreateFiles.jsx`): at the top and the bottom of the Export Center and at the bottom of Prepare migration; once the files exist it offers Download all and "Start the import wizard".

## Invoice rules (v2, `server/src/vouchers.js`, rules in `server/src/defaults.js` 14 and 15)

The first real import refused every invoice. The Invoices file now follows the rules researched in `docs/ZOHO_IMPORT_RULES.md` (8.4):

- **Item Name on every line.** A stock item line carries the Tally stock item. Any other line carries a SERVICE ITEM named after its account (the account name as written, without line breaks, at most 100 characters; " (service)" is added when a stock item has that name). Each service item is added to the Items file after the stock items: Rate 0.00, Item Type "Sales", Product Type "service", Account = that account (flag `service_item_for_account`, one per file). Only the items of invoices really written are added (a journal first tried as an invoice and then written as a Manual Journal adds none). Bills keep account-only lines: Item Name is optional in Zoho's bill sample, and a "Sales" item on a bill would be refused (BIL-ITEM-PURCHASE-INFO). The completeness table explains the extra Items rows (`service_items`).
- **TDS deducted by the customer** (a Tally TDS-type ledger, or a ledger named like Zoho's own "TDS Receivable" account that is not GST in Tally, on the customer's side) goes to the invoice's TDS Name, TDS Percentage, TDS Section Code and TDS Amount, from TDS mapping; with no mapping, the Zoho TDS tax suggested from the section in Tally (`tds_name_default`, unconfirmed); with neither, a negative line flagged `tds_not_mapped`. The invoice total (lines + tax - TDS) is Tally's customer amount; the TDS posts to TDS Receivable (voucher reconciliation role `tds_column`).
- **Round-off** (a ledger of Tally type Invoice Rounding: `roundingmethod` set to a method) goes to Adjustment, the same value on every row of the document, with Adjustment Description "Round Off" on invoices (the bill sample has no description column); flag `round_off_adjustment`, role `adjustment_column`. The import notes of the file and the wizard's set-up step say to tick Adjustments (Settings > Setup & Configurations > General).
- **A line with no GST** gets Zoho's zero-rate tax: GST0 when the place of supply is the company's state (Tally's `cmpgststate`), IGST0 otherwise and for an export (`invoice_line_zero_tax`, unconfirmed). A line whose GST exists but could not be put on it is never given a zero rate.
- **Any other negative line** stays a line, flagged `negative_row`; the Zoho check calls it "may be refused" (INV-NEGATIVE-LINE, BIL-NEGATIVE-LINE). The Zoho check also checks that an invoice's Item Name is in the Items file (INV-ITEM-EXISTS, may be refused). Rules version 1.2.

## Simpler decision screens (v2)

- **Tax mapping** is automatic: every GST ledger is written with Zoho's own tax of the rate of each line (CGST and SGST -> GST<rate>, IGST -> IGST<rate>; output and input alike). The rate per ledger comes from Tally's rate on the lines, else the ledger's own rate, else the amounts of a one-line document (tax usage, `taxes.js`, worked out again once for data processed before). `GET /tax-mappings` adds `kind` (gst, tds, other), `head`, `rates` ([{ rate, vouchers, auto }]), `autoNames`, `source` (explicit, auto, none), `written`, `needsPerson` and `needsPersonWhy`. Only a GST ledger with no rate in Tally, a rate Zoho has no tax for, or a cess needs a person (Prepare migration counts only those). TDS ledgers go to TDS mapping; other duties (professional tax) post as accounts and are never asked. `GET /tax-choices`: Zoho's default GST and IGST taxes (`zohorules.json` default_taxes), the saved Zoho tax list, and the TDS pick list. An explicit mapping stored earlier always wins.
- **TDS mapping**: a pick list (`TDS_CHOICES`: the names in Zoho's samples and the descriptions of Zoho's TDS section codes, with the old sections they stand for); each ledger has a `suggestion` from its section (Tally's nature of payment, else a section number in its name), `source` and `written`. A change marks Bills and Invoices out of date.
- **Fix contacts**: each row also has `pan` ({ tally, written, fromGstin, source }), `sameGstin` (other contacts of the same kind with the same GSTIN; problem `same_gstin`) and `written.state`. A PAN can be corrected (`pan` in PUT/PATCH; 10 characters; refused when it is not characters 3 to 12 of the GSTIN). With no PAN in Tally the PAN in the GSTIN is written (`pan_from_gstin`).
- **Accept as per Tally**: `GET /api/migrations/:id/reviews`, `PUT /api/migrations/:id/reviews/:step` `{ accepted }` records that a decision step was reviewed and the defaults and Tally values stand (audited `step_accepted_as_tally`); Prepare migration shows it on the item (`reviewed`). Viewers read only.
- Screens: Fix contacts is a compact sheet (twenty rows, click to expand, filter by a problem count, select and one action for all); tax and TDS mapping are compact tables with pick lists; Rates is one line until opened; Zoho's own accounts is one choice for all.
- Proof on the real data, counts only: `zoho_check_counts.mjs` in the session scratchpad (zero decisions; `--tds` maps the TDS ledgers that have no section).

## Run the whole tool on a folder of Tally files (`server/scripts/real-run.mjs`)

One command runs the tool from upload to the zip, in-process (no server, no browser, no login screen), and writes everything it produces to a folder. Use it to check a change against a real company before anyone imports into Zoho Books, and to compare two runs.

```bash
cd server
node scripts/real-run.mjs <tally-folder> <output-folder>
```

- `<tally-folder>` holds the TallyPrime JSON exports: `Master.json` (All Masters), `Transactions.json` (all transactions of the year) and `TrialBal_ledgers.json` (the detailed Trial Balance; `TrialBal.json` is used when that file is not there). The folder is only read, never changed.
- `<output-folder>` is created. It gets `zoho-import.zip` (the same zip as Download all: `READ_ME_FIRST.txt`, `READ_ME_IMPORT_ORDER.txt`, the files numbered in import order, `not_for_import/`), every import file in `csv_files/` (with `credits_to_apply.csv`, `predicted_trial_balance.csv` and any lists of held vouchers), and the answers of the API as JSON: `_import_wizard.json` (every wizard step), `_zoho_check.json` and `_zoho_check_findings.csv`, `_assumptions.json`, `_completeness_table.json`, `_voucher_reconciliation.json`, `_held_vouchers.json`, `_credits_to_apply.json`, `_trial_balance.json`, `_predicted_trial_balance.json`, `_bank_opening_balances.json`, `_tds_taxes_to_create.json`, `_summary.json`, `_report.json`. `_run_log.txt` lists every call with its status code.
- It uses a new temporary data folder (`DATA_DIR`), so `server/data` is never touched, and signs in as the first super admin of `seed-users.json`.
- It follows the zero-decision path: the tool's defaults, "registered without GSTIN = unregistered" (Fix contacts), the HSN/SAC field on with 6 digits, every set-up tick of the Import Wizard ticked, and the default wizard answers (for example a reverse charge vendor with no GSTIN and no state is an import of services). The Stock Summary is waived as not needed.
- To prove a change, run it into a new folder and compare with an earlier run, file by file (for example `diff` on `csv_files/`, or the counts in `_import_wizard.json` and `_predicted_trial_balance.json`).
- The output holds the company's real data (names, GSTINs, amounts). Keep it out of the repository, the tests and the documents.

## HSN/SAC, Migration Date and GST ledgers (S3)

Three things found by the second Zoho import test, handled for any company (no party, ledger, GSTIN, state or code of the test company is in the code; the rules read Tally fields and tables in `server/src/zohorules.json`).

**HSN/SAC.** A new Zoho Books (India) organisation has "Enable the HSN Code or SAC field" switched ON. Zoho then refuses an invoice line with an empty HSN/SAC or one of 5 digits ("Please ensure that the length of the HSN code is a minimum of 6 digits and it has only numbers."; 26 invoices in test 2). It does NOT "not matter" that the code is empty.
- Import Wizard, set-up step: the question "Is the HSN Code or SAC field switched on in your Zoho Books?" (default yes) and, when yes, "How many digits?" (6, or 4). Stored as the voucher settings `hsnEnabled` and `hsnMinDigits` (`PUT /api/migrations/:id/voucher-settings`); changing them makes the Items, Invoices and Bills files out of date. The set-up guide says how to switch the field off in Zoho Books (Settings > Module Settings > General > Items, tab Preferences). When the answer is No, the HSN/SAC column is written empty and nothing is flagged.
- When it is on, each invoice line gets: Tally's code if valid, else the code chosen for its item, else the code chosen for its income ledger (Mapping Studio > HSN/SAC, `PUT /api/migrations/:id/hsn-defaults` `{ defaults: [{ kind: 'item' | 'account', name, code }] }`, a code is 4, 6 or 8 digits and at least as long as the organisation takes), else a SAC suggested from the words of the name (`lists.sac_suggestions`, evidence "assumed", shown highlighted and listed under Assumptions as `hsn_suggested`), else nothing and a blocking flag (`hsn_missing_required`). Service items made for invoice lines carry the same code. Bills use Tally's code or a chosen code only: a suggestion is never made for a purchase.
- Zoho check: `INV-HSN-REQUIRED-WHEN-ENABLED` (confirmed by test 2, so it blocks the download) and `BIL-HSN-REQUIRED-WHEN-ENABLED` (assumed) predict the refusal of an empty or short code while the answer is yes. Error message added to the Rejection Manager.

**Migration Date (Opening Balance Date).** Zoho Books keeps one date for the opening balances of customers and vendors. Observed in test 2: Settings > Setup & Configurations > Opening Balances cannot save the date alone ("Please enter the opening balances for the accounts to continue"), and with the date never saved the contacts' balances landed outside the financial year. Zoho's help says the date is the date of the trial balance taken from the old software and that bank and credit card accounts, items with stock and contacts with balances should exist first (https://www.zoho.com/in/books/kb/opening-balance/ob-for-migration.html, https://www.zoho.com/in/books/help/settings/opening-balances.html).
- The old set-up step "Opening Balance Date" is gone (it could not be done before any balance exists). A wizard step "Save the Migration Date" comes after the Chart of Accounts and the bank accounts and before Customers and Vendors. It shows the date, the click path and a real balance to type (the smallest bank balance first). It is NOT confirmed that Zoho accepts the balance being set back to 0 afterwards; the step says to do that only when the tool's opening balance journal carries the same balance, so the Zoho trial balance comparison shows any mistake.
- The date: the day before the financial year starts (the date of the opening balance journal), or the date typed in the step (`openingDate` voucher setting, year-month-day). The journal (`opening_balances_for_zoho_accounts.csv`) is dated with it; changing it makes that file out of date.
- A Customers or Vendors file with opening balances stays locked in the wizard until the step is ticked (open it with a typed reason if the date was saved some other way). The Zoho check warns (`CUS-OPENING-BALANCE-DATE`, `VEN-OPENING-BALANCE-DATE`) while it is not ticked.

**Tally GST ledgers and Zoho's own tax accounts.** Invoices and bills post to Zoho's system accounts (Input CGST, Output IGST ...). A Tally ledger such as "Output CGST@9%" written as an ordinary account was filled by journals while Zoho's own account was filled by invoices, so both showed a balance. Now:
- `server/src/taxaccounts.js` tells, from the Tally ledger master (group chain reaching Duties & Taxes, type of duty GST with its duty head, TDS type, "is input credit" or the words input/ITC in the name because Tally often leaves the field false), which Zoho account a duty ledger belongs on; the table is `lists.tax_ledger_zoho_accounts` (evidence: `lists.default_accounts`). CGST, SGST/UTGST and IGST on the output or input side are certain: the ledger is NOT written to the Chart of Accounts, its opening balance goes to the opening balance journal on Zoho's account, and journals use Zoho's account name (assumption `tax_ledger_to_zoho_account`). Cess, reverse charge and TDS ledgers are only suggested (`tax_ledger_needs_decision`): they stay accounts of their own until a person chooses "Use Zoho's account" in Mapping Studio > Zoho's own accounts, which also shows why each ledger was mapped and lets a ledger be renamed to stay an account of its own. If the organisation's Chart of Accounts export is given and lacks the Zoho account, it is not applied.
- Trial balance comparison: a Tally GST ledger is compared with its Zoho tax account, several ledgers as one total. A Zoho Trial Balance export for a date range shows only the activity inside the range (observed in test 2), so the period in its title ("From dd/mm/yyyy To dd/mm/yyyy") is read and a warning says to export again with a From date before the opening date, or to use the as-of view. The export layout (Account, Net Debit, Net Credit, with group heading rows) is now checked against one real export.

## Held vouchers built from an uploaded sample

Zoho Books does not publish the import columns of Payments Received, Payments Made, Vendor Credits and Credit Notes, and `zoho-samples/` has none of the four samples. No column is invented. In the Export Center (held vouchers) the user uploads the sample that Zoho Books gives on the module's Import screen (`PUT /api/migrations/:id/zoho-samples/:module`). The answer says at once whether the file can be built:

- Payments Received and Payments Made: the tool reads the sample's heading row (`server/src/heldfiles.js`), writes a file with the same headings in the same order, one row per payment or per invoice or bill applied (`GET /api/migrations/:id/held-vouchers/:module/zoho-file`; the file is also in the zip). A heading it does not recognise is written empty and listed. If the date, party, amount or bank or cash account heading is missing, nothing is built and the answer names the missing meaning and the headings seen. A voucher with lines besides the party and the bank stays held. Payment Mode is written as Others.
- Vendor Credits and Credit Notes: the sample is kept and the module stays held (see docs/ZOHO_IMPORT_RULES.md).
- The meanings of the fields come from Zoho's API and help pages and are in `zohorules.json` (`lists.held_modules`, evidence "Zoho documentation"); the words that recognise a heading are marked "assumed".

## Repair round after review (any-company rules)
- **HSN/SAC default.** `hsnFieldOn` (`server/src/vouchers.js`) is the one place that decides whether the HSN/SAC field is taken as on: an Import Wizard answer wins; with no answer a company with a GSTIN is on and a company with no GSTIN is off. The Zoho check, the wizard, the voucher settings and the decisions all use it.
- **Bill HSN rule.** `BIL-HSN-REQUIRED-WHEN-ENABLED` is now a warning with evidence "Contradicted by second import": test 2 imported bills with an empty HSN/SAC. The invoice rule is unchanged.
- **TDS names.** A TDS tax name used in one run for another rate or section is made unique among the taxes the tool creates too (first tax keeps the plain name). TDS deducted by a customer with no section no longer falls back to Professional Fees: a rate that fits a section of the table picks it (flag `tds_section_ambiguous` when several fit), a rate that fits none is left for Mapping Studio.
- **GST ledger side.** The side (input or output) comes from Tally's field first; without it from the name and the side of the opening balance together. If they disagree the ledger is only suggested (listed, not moved by default).
- **Migration Date.** (Replaced in rules 1.8.) No balance is typed and none is set back: the Chart of Accounts import creates the opening balance record, the person only edits the date, and the step is done when the date Zoho Books shows is typed and equals the Migration Date. Every later file is locked until then.
- **Zip read-me.** READ_ME_FIRST.txt and READ_ME_IMPORT_ORDER.txt now have a section "Vouchers that are not in any file" with counts, the reason and the sample to upload.
- **Registered with no GSTIN.** Now a blocking assumption; Fix contacts has one button that treats all of them as unregistered.
- **Reverse charge, vendor with no state.** The Import Wizard asks (only when such bills exist) whether these vendors are outside India.
- **Tax ledgers left as own accounts.** Prepare migration counts them and says the Zoho trial balance will differ on them until they are merged or accepted.
- **Held payment files.** Cells are written by column position (a repeated heading no longer copies a value); totals use exact decimals.

## Docs and Import Wizard integration (rules version 1.10)

- **While you import.** The lessons of the test imports that are about the import itself are one list in `zohorules.json` (`general.while_importing`): read the counts after the import (the preview said "ready" for a customer Zoho Books then did not create), a journal refused with "Invalid row" and "- Contact Name" names a contact that is missing (the only refusal of the third test import), a journal with a contact on Accounts Receivable or Payable and a bank line is accepted, "Nothing handled the action gotoImportPreview" on Zoho's page means reload the page, and give the error file to the tool.
